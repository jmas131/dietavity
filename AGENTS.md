# Dietavity Repository Operating Contract

## Scope and priorities

- Treat this file as the default contract for all repository work. A more specific nested `AGENTS.md`, if one is added later, governs only its subtree.
- Inspect the current implementation before editing. Prefer current code, migrations, tests, and generated artifacts over historical docs or ticket-numbered assumptions.
- Make the smallest robust change that satisfies the request. Do not redesign adjacent systems or implement unrequested product ideas.
- Prioritize correctness, security, idempotency, observability, maintainability, performance, and then launch speed. Do not create a parallel framework, database, queue, persistence layer, workflow engine, AI architecture, or messaging path when the existing stack can safely meet the requirement.
- Developer-facing code and documentation are English. Customer-facing copy is concise, natural Mexican/Latin American Spanish unless the product explicitly supports another language.

## Repository sources of truth

- Node/Express website and backend routes: `server.js`, with shared code in `lib/` and views in `views/`.
- Sales policy: `lib/sales-engine-v3.js`; shared offer/product facts: `lib/dietavity-knowledge.js`.
- n8n production-target artifacts: `n8n/`. Determine the current canonical workflow before every workflow change; do not patch similarly named files in `archive/` or old ticket artifacts.
- At this file's creation, the current canonical Sales Engine workflow is `n8n/Dietavity Sales Engine (Ticket 10).json`. It is generated by `scripts/refactor-ticket-10-workflow.js` from `n8n/Dietavity Canonical Ledger (Ticket 9).json` plus the current `lib/` policy/knowledge modules.
- Database structure: migrations in `database/migrations/`; canonical schema snapshot: `database/schema.sql`.
- Automated regressions: `test/*.test.js`, with workflow helpers in `test-support/`.
- Deployment information is documented in `docs/DEPLOYMENT.md`; documentation may lag the executable repository, so verify commands and artifact names before relying on it.

## Change and generation discipline

- When changing a generated n8n workflow, change its source module or generator, regenerate the JSON, keep both synchronized, and test the generated artifact. Do not hand-edit only the output or leave the committed output stale.
- Keep import-ready workflows inactive unless the user explicitly authorizes activation. Tests passing is not deployment authorization.
- Preserve compatibility with the project's actual self-hosted n8n runtime and existing node syntax. Do not silently adopt newer cloud-only behavior or upgrade workflow nodes.
- Database structural changes require a new migration and a synchronized `database/schema.sql`. Never silently change constraints, indexes, grants, RLS policies, or schema only in the snapshot.
- Before using `ON CONFLICT`, verify the real constraint/index and any partial-index predicate. Supabase `upsert({ onConflict: ... })` cannot represent every partial-index conflict target; use a backend RPC where the exact Postgres semantics require it.
- Do not weaken, delete, broadly skip, or trivialize meaningful tests to make a change pass. Update expectations only for an approved behavior change and retain regression value.

## Sales Engine invariants

- Do not redesign the Sales Engine during unrelated work. AI interpretation may assist, but deterministic policy remains authoritative for Checkout authorization, material commercial questions, contextual confirmation, ambiguity, objections, safety boundaries, unsupported claims, and internal identifiers.
- Ambiguity never authorizes Checkout. Authorization is limited to an explicit current purchase request or a valid strong affirmation in the current purchase-confirmation context.
- Weak acknowledgements such as `ok`, `okay`, `perfecto`, `vale`, `listo`, and `gracias` never independently authorize Checkout. New intents and classifiers must not bypass this rule.
- Interpret short replies using the latest actionable assistant question and valid current commercial context. Newer authoritative conversation state outranks stale AI metadata. A short reply is not automatically weak, but ambiguous context must never become purchase authorization.
- Customer-facing sales messages contain at most one actionable question, placed at the end. Preserve this in prompts, deterministic copy, validators, normalization, and fallbacks.
- Keep Stripe Checkout retry-safe. Webhook retries must not create duplicate Checkout Sessions, URLs, replies, or funnel events. Checkout URLs are customer-visible content and belong in the canonical outbound ledger.

## Canonical WhatsApp ledger and side effects

- `messages` is the canonical ledger for actual inbound and intended/final outbound WhatsApp communication. `onboarding_chat_memory` is AI context, not evidence of the final text Dietavity sent.
- Persist the final post-policy, post-validator, post-fallback customer-visible response—not merely raw model output—when the path is AI generation -> deterministic policy -> validation/normalization -> Twilio.
- A real Twilio inbound Message SID must map to one canonical inbound reservation and at most one customer-facing side-effect path. Never substitute an n8n execution ID or invented value when provider identity is required; fail safely if it is absent.
- Reserve the final outbound body canonically before sending under the existing design, then persist Twilio SID/status when available. If Twilio may have accepted a message but persistence failed, reconcile ambiguous provider state instead of blindly resending.
- `sales_funnel_events` is idempotent business evidence, not a conversation ledger. Follow existing event-key conventions and store only operationally necessary metadata—never full conversations or unnecessary profile/health data.
- Conversations may precede a `users` row. Do not assume every message has `user_id`; preserve normalized WhatsApp/session identity and the existing post-purchase linkage of historical session messages.
- Preserve controlled customer behavior, structured operational evidence, and duplicate-side-effect prevention. Do not turn genuine database/provider/infrastructure failures into silent success. Keep the `n8n/Global Error Handler.json` architecture unless explicitly changing it, and keep secrets and sensitive profile data out of logs.

## Database and security boundaries

- Supabase/Postgres application tables are backend-only. Preserve RLS, grants, service-role boundaries, deliberate `SECURITY DEFINER` RPCs, and API authorization. Never expose protected tables to `anon` or `authenticated` clients for convenience.
- Use existing environment/configuration conventions. Never hard-code or commit API keys, Supabase service-role keys, Stripe secrets, Twilio tokens, credentials, or production secret values; do not invent credentials or propagate any accidentally displayed secret into docs, fixtures, logs, or output.
- Apply data minimization. Do not expose internal identifiers to customers without need, introduce casual third-party sharing, or copy sensitive profile data into analytics/funnel metadata.

## Setup, program, and legacy lifecycle

- Detailed personalization and health-related profile data belongs in the post-purchase Setup flow, not ordinary pre-purchase sales chat. Do not solicit weight, height, age, conditions, medications, or detailed restrictions before purchase unless an explicitly approved feature requires it.
- Preserve Setup's explicit sensitive-data consent, server-controlled consent timestamp, privacy-notice version, backend validation, retry-safe completion, and idempotent `setup_completed` event persistence.
- Preserve the current separation among purchase/payment state, Setup/profile state, a program, its four weeks, and weekly meal plans/shopping data. The default product model is one 28-day program with four program weeks; do not collapse or duplicate these concepts without architectural justification.
- Legacy recurring subscriptions and current one-time 28-day purchases are distinct. Do not remove or rewrite legacy cancellation during unrelated work, route one-time purchasers through recurring cancellation, delete a user on cancellation, or delete historical/customer data that the existing cancellation architecture preserves.

## Product, AI, and nutrition truthfulness

- Describe only capabilities implemented by Dietavity. Future concepts are not current features.
- Never invent human nutritionist review, doctor supervision, clinical treatment, professional credentials, guaranteed health/weight outcomes, or proprietary medical, nutritional, or culinary databases.
- Be transparent about AI when asked. Do not imply that a human individually creates each program, conceal AI involvement, or fabricate credentials.
- Dietavity provides general nutrition support, not individualized medical care. Do not claim deterministic clinical calorie or macro prescriptions, age-specific micronutrient prescriptions, medication changes, disease treatment, or clinical nutrition therapy unless an explicitly approved, executable implementation actually supports the claim.
- Personalization may consider declared allergies, restrictions, conditions, and profile information only within implemented logic; customer wording must not overstate that logic.

## Production boundary

- Repository work authorizes preparation and local validation only. It does not authorize production changes.
- Unless the user explicitly requests the specific production operation, do not import, activate, or deactivate production n8n workflows; deploy or restart services; run production migrations or mutate production data; delete production users; change Stripe products/prices/configuration; change Twilio configuration or send production WhatsApp messages; modify production environment variables or rotate credentials; alter nginx, PM2, or hosting configuration; or perform destructive infrastructure operations.
- Implementation and deployment are separate phases. It is safe to prepare code, migrations, workflow JSON, SQL, tests, and deployment instructions; report any required production steps separately.

## Required workflow for implementation tickets

1. Inspect the current architecture and reproduce or understand the behavior.
2. Identify the root cause and affected invariants.
3. Implement the smallest robust fix and add focused positive, variant, and negative regressions. For production incidents, include the exact incident or a faithful sanitized equivalent when practical.
4. Run focused tests, then relevant historical suites, then the full supported suite. Completion target: zero failures and no relevant unexplained skips.
5. Report code changes, validation results, any unresolved discrepancy, and deployment steps separately.

Verified commands:

```bash
# One focused test file
node --test test/<name>.test.js

# Full canonical regression suite (package.json -> node --test)
npm test
```

Do not introduce a major dependency or external service without explaining why the existing stack is insufficient and comparing reliability, complexity, performance, cost, operational burden, migration risk, and architectural fit.
