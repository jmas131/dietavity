# Dietavity n8n Documentation

This document describes the purpose and organization of the n8n workflows used by Dietavity.

---

# Overview

n8n is the orchestration layer of Dietavity.

It is responsible for integrating all external services, processing user requests, executing AI workflows, and synchronizing data between the different systems.

---

# External Services

The workflows integrate with:

- Twilio WhatsApp API
- OpenAI API
- Supabase
- Stripe
- Node.js Website

---

# Workflow Files

## Dietavity Sales Engine (Ticket 10).json

Current canonical production-target workflow artifact. The committed artifact is
inactive and is generated by `scripts/refactor-ticket-10-workflow.js` from
`Dietavity Canonical Ledger (Ticket 9).json` together with the current shared
Sales Engine policy and product-knowledge modules in `lib/`.

Responsibilities include:

- Receive WhatsApp messages
- Reserve canonical inbound messages before customer-facing side effects
- Load user profile
- Route sales leads, one-time purchasers, and eligible legacy subscribers
- Build AI prompts
- Apply deterministic Sales Engine and Checkout policy
- Generate meal plans
- Generate recipes
- Generate shopping lists
- Process ingredient swaps
- Store final customer-visible WhatsApp messages in the canonical message ledger
- Update Supabase
- Reserve and send WhatsApp responses and persist delivery results
- Process one-time Stripe purchases and preserve legacy subscription handling
- Orchestrate 28-day program generation and weekly progression

---

Responsibilities:

## Dietavity Weekly Conversation & Sales Intelligence.json

Independent, read-only scheduled workflow introduced by Ticket 19 and evolved
by Ticket 32. It is distinct from the general `Dietavity Weekly Report.json`.

Responsibilities:

- Run once per week on Monday at 08:00 using the `America/Mexico_City` workflow
  timezone.
- Query customer-visible fields from canonical `public.messages` for the
  previous seven complete local calendar days. The half-open UTC-instant
  boundaries are derived from local midnights, and the partial execution day is
  excluded.
- HMAC-pseudonymize session identifiers with
  `DAILY_AUDITOR_HMAC_SECRET` and redact obvious contact/token data before the
  single AI request.
- Reconstruct complete customer-visible conversations chronologically and
  analyze intent, funnel signals, objections, sales behavior, marketing and
  positioning insights, product/customer-experience lessons, and genuine
  technical defects.
- Use canonical offer, positioning, and medical-scope facts generated from
  `lib/dietavity-knowledge.js`. Unverified capabilities are explicitly marked
  for verification rather than assumed.
- Treat single conversations as isolated observations by default, show sample
  quality and evidence strength, and do not exclude possible test traffic
  without reliable metadata.
- Email a concise report with no mandatory engineering ticket. At most one
  ticket may be proposed for a supported technical defect; it is advisory,
  requires human approval, and never changes repository or production state.
- Skip the AI request and send a minimal report when the period has no messages.

The committed workflow is inactive. Before an authorized production import,
configure `DAILY_AUDITOR_HMAC_SECRET` as a random secret of at least 32
characters in the n8n environment and allow the built-in `crypto` module in Code
nodes (for example, `NODE_FUNCTION_ALLOW_BUILTIN=crypto`) if the self-hosted n8n
runtime does not already allow it. The OpenAI key and existing Postgres/SMTP
credentials remain outside model prompts. The workflow delegates failures to
the existing Global Error Handler.

Regenerate and verify the import artifact with:

```bash
node scripts/refactor-ticket-32-weekly-conversation-sales-intelligence.js
node scripts/refactor-ticket-32-weekly-conversation-sales-intelligence.js --check
```

Ticket 19A keeps the OpenAI request as ordinary JSON in the HTTP Request node.
Only `system_message` and `user_message` are n8n expression slots, and each is
inserted with `JSON.stringify(...)` so arbitrary sanitized prompt text remains a
valid JSON string. Do not replace this with a monolithic `={{ ... }}` object
expression; n8n 2.34.5 rejects that construction before issuing the request.

# Main Workflow Flow

```
WhatsApp Message
        │
        ▼
Twilio Webhook
        │
        ▼
Canonicalize and Reserve Inbound Message
        │
        ▼
Load User and Route Current State
        │
        ▼
Sales / Paid Assistant / Legacy Subscription Branch
        │
        ▼
Deterministic Policy and AI Processing
        │
        ▼
Reserve Final Customer-Visible Response
        │
        ▼
Twilio Send and Delivery Update
```

Stripe Checkout events, program-generation webhooks, and scheduled weekly
program updates enter through their own triggers in the same canonical workflow.

# Environment Variables

The following credentials are required inside n8n:

- OpenAI
- Supabase
- Twilio
- Stripe

Credentials should be managed using n8n's built-in Credentials system.

Never hardcode secrets inside workflow nodes.

# Deployment

Repository preparation and production deployment are separate phases. For a
change to the current generated canonical workflow:

1. Modify the relevant shared implementation or
   `scripts/refactor-ticket-10-workflow.js`.
2. Regenerate `n8n/Dietavity Sales Engine (Ticket 10).json` with
   `node scripts/refactor-ticket-10-workflow.js`.
3. Confirm that the generated artifact remains inactive.
4. Run focused workflow regressions and the full repository test suite.
5. Commit the source and generated artifact together.

Do not import or activate the workflow in production unless the user explicitly
authorizes those production operations. When production deployment is
authorized, verify credentials and runtime compatibility, import the tested
artifact, activate it deliberately, and run the approved smoke tests.

---

# Best Practices

- Keep workflows modular.
- Reuse sub-workflows where appropriate.
- Name nodes clearly.
- Document complex Function/Code nodes.
- Remove disabled or unused nodes before deployment.
- Keep each committed workflow artifact synchronized with its generator and
  shared source modules.

---

# Error Handling

All unexpected errors should be routed through the Global Error Handler workflow whenever possible.

The objective is to:

- Prevent silent failures.
- Preserve user experience.
- Facilitate troubleshooting.

---

# Version Control

The `n8n/` directory contains the version-controlled workflow definitions.
Generated workflow artifacts must remain synchronized with their generator and
shared source modules.

Every approved production workflow change should be represented by synchronized,
committed source and workflow artifacts in the repository.

Determine the current canonical production-target artifact from the repository
before editing. Do not select an archived or similarly named workflow merely
because its filename contains a version or ticket number.

---

# Future Improvements

Potential future enhancements include:

- Breaking the main workflow into smaller reusable workflows.
- Centralizing shared prompt construction.
- Introducing automated workflow testing.
- Reducing duplicated logic across branches.
- Gradually migrating suitable business logic to Node.js only when it provides a clear maintainability or scalability benefit.

Until then, n8n remains the primary orchestration layer for Dietavity.
