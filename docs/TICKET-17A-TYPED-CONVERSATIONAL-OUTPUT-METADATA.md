# Ticket 17A — Typed Conversational Output Metadata

`public.messages` remains the canonical communication ledger. Ticket 17A adds a prospective, backend-only metadata relation: `conversation_artifacts` references one outbound anchor message and its existing `logical_reply_key`; `conversation_artifact_lineage` records ordered source artifacts. No message body is duplicated.

An artifact is non-authoritative content. Its type and lineage permit later bounded display or transformation, but never establish product truth, policy, safety, authorization, delivery, or execution. Provider acceptance and handset delivery remain fields on `messages`.

The closed output types are `draft` and `summary`. Persisted producing operations are `draft`, `transform`, and `summarize`; `show` reuses the original artifact and creates no new semantic artifact. Each artifact also has a stable non-authoritative `generation_task_id` (`cgt-*`): it distinguishes a producing task instance from both its operation and its persisted artifact. A multipart reply is anchored to its first canonical message and identified by the existing logical-reply key; future writes must reserve all message parts and artifact metadata in one transaction.

Legacy messages have no artifact row and are not eligible artifacts. Future Ticket 60A may project only typed rows and ordered lineage joined to their anchored canonical messages; it must not classify historical prose. `persist_conversation_artifact(jsonb)` is the sole runtime persistence boundary: it validates the anchor, logical reply, ordered lineage, idempotent identity, and graph cycle before inserting both tables atomically. An idempotent retry is identical only when metadata and ordered lineage match exactly. Tables are backend-only and direct service-role mutation is revoked; delivery state is never changed by this RPC. Full graph-cycle prevention and validation that an anchor is the first outbound part occur in the RPC because ordinary row checks cannot safely inspect sibling messages.

Runtime semantic immutability does not prevent privileged privacy deletion. An anchored message is deletion-restricted while typed artifact metadata exists, so the ordinary `service_role` message grant cannot erase semantic history indirectly. The ungranted, `SECURITY DEFINER` `delete_message_with_conversation_artifacts_for_privacy(uuid)` boundary recursively removes only the anchor's dependent artifact graph and then deletes that canonical message atomically. It is reserved for a privileged privacy lifecycle caller; normal runtime roles cannot execute it. Dependent lineage rows cascade with the deleted artifacts, while unrelated graphs remain intact.

Storage alternatives considered: columns on `messages` would repeat logical metadata across multipart rows and make lineage integrity weak; the existing free-form `metadata` JSONB cannot enforce foreign-key lineage. The dedicated one-to-one metadata table preserves message identity, idempotency, recovery data, and queryability without creating another content ledger.
