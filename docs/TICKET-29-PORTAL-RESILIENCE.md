# Ticket 29: portal request resilience

## Runtime design

`GET /p/:token` has one 8,000 ms application deadline, configurable with
`PORTAL_REQUEST_TIMEOUT_MS` from 100 through 30,000 ms. The production value
must remain comfortably below nginx's upstream timeout; this ticket does not
change nginx configuration.

Every PostgREST query used to render the portal receives the same
`AbortSignal`. When the total budget expires, the controller aborts the active
HTTP request and the route returns a branded `503 Service Unavailable` response
with `Retry-After: 60`. A guarded deadline race ensures Express can respond even
if an HTTP adapter fails to settle after abort; the losing query always has a
rejection handler, so it cannot create an unhandled rejection. The one timer is
cleared in the route's `finally` block.

Each completed, failed, or timed-out query writes one JSON diagnostic:

```json
{"event":"portal_query_stage","request_id":"<server UUID>","stage":"portal_program_lookup","elapsed_ms":12,"outcome":"success"}
```

The request ID is generated by the server and returned as `X-Request-ID`.
Diagnostics contain no token, user identity, query values, credentials, error
message, meal data, or profile data. Outcomes are `success`, `database_error`,
and `timeout`.

## Query-plan investigation

Production `EXPLAIN (ANALYZE, BUFFERS)` evidence was not available in the local
implementation environment. Therefore this change does not claim that a
specific query caused the incident and adds no speculative index.

Static schema inspection gives the following expectations, which must be
confirmed against production:

- User by `portal_token`: `users_portal_token_key` is a unique btree index.
- Week by `(program_id, week_number)`: covered by
  `weeks_program_id_week_number_key` and an equivalent unique index.
- Active week by `program_id`: covered by the partial
  `weeks_one_active_week_per_program_idx` index.
- Meal plan by `week_id`: covered for non-null values by
  `meal_plans_one_plan_per_week_idx`.
- Latest program by `user_id ORDER BY created_at DESC LIMIT 1`: no matching
  index exists in the schema snapshot and it is the only portal query with an
  obvious static indexing gap. That gap alone is not evidence of production
  latency.

Before considering an index, run the equivalent portal queries in the
production SQL editor with `EXPLAIN (ANALYZE, BUFFERS)` for a representative
user who has a program. Do not copy the user UUID, portal token, or plan data
into tickets or logs. Record only sanitized plan nodes, scan types, row counts,
buffer counts, planning time, and execution time. Add
`programs (user_id, created_at DESC)` only if that evidence shows a material
benefit and after checking production for an equivalent index.

## Deployment and validation

1. Deploy the application files and set `PORTAL_REQUEST_TIMEOUT_MS=8000`.
2. Restart the application through the normal deployment procedure. Do not
   change nginx timeouts.
3. Open one valid portal URL and confirm HTTP 200 and unchanged plan content.
4. Confirm successful stage diagnostics share one request ID and contain no
   sensitive values.
5. Confirm an invalid token still returns HTTP 404. Exercise timeout behavior
   only in automated tests, not by creating a production database hang.

No migration is required for this implementation. If later production evidence
justifies an index, deliver it as a separate concurrent-safe migration and
synchronize `database/schema.sql`.

## Rollback

Revert the application changes in `server.js`, `lib/portal-deadline.js`, and the
environment entry, then redeploy and restart the application. No database or
nginx rollback is needed because this ticket adds neither a migration nor a
proxy configuration change.
