## Architecture and canonical engine boundary

`n8n/Dietavity Autonomous Conversation Harness (Ticket 48).json` is generated by `scripts/generate-ticket-48-harness.js` from `lib/ticket-48-harness.js`, the scenario library, and the current `n8n/Dietavity Sales Engine (Ticket 10).json`.

```text
Manual Trigger → Load Test Scenario → initialize execution-local batch/session
  → prepare private customer payload → Customer model → strict JSON validation
  → canonical knowledge → canonical classifier model → canonical parser/policy
    → respond/close: canonical response prompt → Sales model → canonical validator
    → Checkout/reminder: intercepted locally, no external action
  → record final visible reply, internal evidence and assertions
  → termination? no: next Customer call
                 yes: separate Judge call → strict validation → scenario report
  → next scenario or final batch report
```

Customer, Sales classifier, Sales response generator and Judge are four distinct calls with separate prompts. They use the canonical model node type/version/settings (currently `gpt-5-mini`, low reasoning effort). They have no tools or shared model memory. The Judge does not reuse the Customer conversation or hidden model context.

The generator embeds the exact canonical knowledge, interpretation parser, deterministic policy, constrained response builder and final validator Code bodies. The canonical interpretation system prompt and model settings are preserved. The classifier receives the current customer message in an explicit JSON envelope. The Sales response call receives its canonical system prompt and a JSON envelope containing the current message plus **final-only** visible history, replacing the Postgres memory subnode. This memory transport is intentionally different from production; the workflow tests canonical conversational decisions and validation, not production delivery, concurrency, persistence or the exact Postgres-memory serialization.

Ticket 41A remains the manual deterministic harness. Its existing entry was inspected but is not invoked: it writes namespaced sessions and AI memory and uses two fixed identities, which is unnecessary for autonomous batches. Both harnesses share the canonical Sales Engine source nodes. Ticket 48 adds an execution-local state adapter rather than copying policy into a separate implementation. It mirrors the current response-state UPDATE (goal, stage, current offer, last question and 30-minute commercial context); a pinned hash makes generation fail if that canonical SQL changes until the adapter is reviewed. No production behavior was modified to make the harness work.

## Scenarios and model contracts

`test-support/ticket-48/scenario.schema.json` defines scenario ID/version, target, offer context, persona, private objectives, behavior constraints, starting message and bounded turn count. The runtime validates the contract before any model call. Defaults are 12 turns; supported bounds are 1–12 turns and 1–8 distinct scenarios. Unknown scenarios, unsupported offer contexts and the future `concierge` target fail closed.

The eight version-1 scenarios in `test-support/ticket-48/scenarios.json` are:

| ID | Main motivation |
| --- | --- |
| `curious_glp1_001` | Understand the service while using supervised GLP-1; no invented medical question. |
| `medication_confusion_001` | Clarify whether the product supplies medication. |
| `price_sensitive_001` | Understand price, inclusions and recurring billing without compulsory purchase. |
| `prepared_food_001` | Find out whether meals are delivered; rejection is valid. |
| `skeptical_ai_001` | Assess value compared with free AI meal ideas. |
| `busy_customer_001` | Assess practical organization and cooking requirements. |
| `context_switching_001` | Switch naturally between price, location and personalization. |
| `medical_boundary_001` | Discuss the product, then ask a medication-management question. |

Scenarios describe motives, not scripted conversations. Future supported offers can be selected through `offer_context` once a real canonical contract exists; unsupported future products are not invented. The runner, transcript, assertions, customer and Judge are separated from the target adapter, but v1 intentionally rejects Concierge and contains no voice/audio handling.

The Customer input is an explicit allowlist of persona fields, private objectives/constraints, starting message and pairs of customer messages/final Dietavity replies. It cannot receive harness/session IDs, offer-context implementation details, engine prompts, buyer signal, strategy, topics, health scope, raw drafts, validator diagnostics or expected answers. Persona subfields are also allowlisted. The Sales calls receive no persona or hidden objectives. The starting message is enforced on the first turn; subsequent messages react to the actual final reply.

Customer output must be exactly:

```json
{"customer_message":"A short message in Spanish","outcome":"continue"}
```

Allowed outcomes: `continue`, `customer_rejection`, `conversation_resolved`. Empty, overlong, malformed, extra-field or unsupported output stops before further Sales execution. The Customer cannot self-authorize Checkout or declare a payment successful.

The separate Judge receives the scenario contract, canonical public product facts, termination reason and customer-visible transcript. It receives no diagnostics, prompts, raw drafts or expected verdicts. Its contract requires the Ticket 48 boolean findings, termination reason and turn-indexed evidence. Wrong types, unknown fields, invalid evidence indexes, unsupported reasons or defects without evidence invalidate the verdict and fail the scenario report. There is no score and no repair/retry model loop. `judge_status` means the output contract validated; actual negative findings still fail the overall report. A correct rejection is not a failure.

## Isolation, assertions and termination

There are **zero application database writes**. State is carried in one execution item; each scenario starts with an empty transcript and a synthetic session key `__harness48__:<execution_id>:<scenario_id>`. The key is diagnostic input only. There are no credentials or nodes for Postgres, Twilio, Stripe, HTTP requests, email, portal/user provisioning, fulfillment, execute-workflow, schedules or production error workflows. Model nodes use the unresolved name `Dietavity Autonomous Harness OpenAI`, without production credential IDs. Existing production model credentials are not silently bound.

As generated, the graph cannot send WhatsApp/email, create Checkout/payment/users/programs, touch orders or leases, or write customer history/events. Only the explicitly mapped model service and n8n's own execution storage are used. This is structural capability exclusion, not a mock of provider delivery and not a claim that model calls are offline. Tests verify the entire graph allowlist, absence of tools and external capabilities, unresolved credentials and canonical Code safety. Editing the imported graph to add tools or side-effect nodes invalidates that guarantee.

Generic Checkout and requested reminders stop at the action boundary. Their `final_dietavity_response` is **null** because downstream customer text was never produced; no fake payment URL or “[TEST ONLY]” message is passed off as something Dietavity sent. Diagnostics preserve the intercepted action. GLP-1 holding-page text goes through the real canonical validator and is captured as visible text, without fetching its URL. No Customer turn runs after purchase interception.

Deterministic checks cover qualifying purchase authorization (including weak acknowledgements and valid contextual confirmations), GLP-1 holding-only behavior, nonempty replies, maximum questions, ambiguous multiple jobs, internal identifiers, known unsupported/medical claims, repeated generic greetings and maximum turns. The no-side-effects check is backed by the graph/code allowlist; it is not a production provider log assertion. Claim and repetition checks are bounded pattern checks, not exhaustive natural-language proofs, and are reported alongside independent Judge findings.

Termination reasons are `purchase_intent`, `customer_rejection`, `conversation_resolved`, `safety_escalation`, `engine_failure`, `max_turns`. Safety escalation records a correct medical referral separately from a safety violation. Model/provider failures and canonical knowledge/policy/validator exceptions stop the conversation and still attempt the Judge. A malformed Judge fails the report while retaining the original termination reason. Provider error bodies are not copied into reports. An infrastructure-wide n8n cancellation or execution timeout can prevent final Judge/report completion; inspect the retained execution in that case.

## Reports, reproducibility and cost controls

Every report retains scenario/version, run ID, termination, outcome, assertion PASS/FAIL, Judge findings/evidence, potential defects, full final-only transcript and per-turn diagnostics. Diagnostics include all Ticket 48 fields, intercepted action, parsed interpretation, the input session state and timestamps. Failed engine turns preserve the pending customer message and available interpretation/decision separately instead of inventing a reply.

Metadata includes Customer/Judge prompt text and versions, canonical artifact name/hash, canonical classifier prompt, configured model settings, state-SQL hash, adapter version, library hash and harness-source hash. Saved sessions/drafts aid deterministic regression reproduction; the full scenario contract supports exploratory replay. Replay the saved scenario against its recorded canonical artifact to avoid silently testing a newer contract. Time-sensitive regression tests should use the recorded timestamps with the test runner's injected `Date`. Exact stochastic reproducibility is explicitly **false**; no supported seed is claimed.

The batch summary includes scenario count, passes, potential defects, engine/Judge/safety failures, unexpected commercial transitions, purchase-intent outcomes, rejections, safety escalations, max-turn terminations and model calls. Each report labels synthetic outcomes as non-market evidence.

Maximum logical model invocations are `3 × max_customer_turns + 1` per scenario: at most 37, or 296 for eight scenarios. Checkout interception avoids an unnecessary response call. Agent iterations are limited to one, node retry is disabled, the generated workflow has an 1,800-second timeout, and there is no recursive execute-workflow or schedule. Provider SDK transport retries, if any, are not individually counted; configured canonical model behavior is preserved. Available token-usage fields are summed. If n8n does not expose them, totals are explicitly incomplete rather than represented as zero-cost usage. No currency cost or exact usage is invented.

Use saved n8n manual execution data and export **Test Report** JSON before execution-data pruning. Local fixture output can be saved with `--output`; this uses exclusive creation so an old report is not silently overwritten.

For a separately authorized n8n acceptance run:

1. Import the Ticket 48 JSON as a **new** workflow, preferably into an isolated test n8n instance. Keep it inactive. Do not replace Ticket 41A or Sales Engine, attach an error workflow, or add tools/delivery/database credentials.
2. Map only **Dietavity Autonomous Harness OpenAI** on the four model nodes. Retain canonical model settings, or record any deliberate model configuration changes in the exported report; the generated metadata reflects the artifact's settings.
3. Leave **Load Test Scenario** at the single `curious_glp1_001` selection and 12 turns. Execute manually. Inspect actual final replies, Customer reactions, diagnostic fields, termination, Judge and Test Report. Confirm the live transcript reaches at least three customer turns to satisfy the ticket's initial acceptance example. Do not force an otherwise resolved conversation to buy or continue merely to hit the example length.
4. After inspecting that run, change only `scenario_ids` in **Load Test Scenario** to the eight IDs listed above and execute manually again. Export the full report. Each scenario is sequential and starts with fresh execution-local state.
5. Inspect any FAIL as a potential defect, retain its scenario/artifact/prompt/model metadata and transcript, and create a reproducible regression before considering a production change. A well-handled rejection or medical referral is not a sales defect.

No migration or production deployment step exists. For removal, delete the inactive Ticket 48 workflow and its synthetic n8n executions as desired; delete the local fixture reports when no longer needed. No database cleanup is necessary. Repository rollback consists of removing the newly added Ticket 48 runtime, generator, workflow, tests, scenario/schema/runner files, fixture CLI, reports and this runbook. Existing production artifacts require no rollback because they were not changed.
