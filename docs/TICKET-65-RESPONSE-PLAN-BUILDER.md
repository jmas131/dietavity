# Ticket 65 — Deterministic ResponsePlan Builder

`buildResponsePlan` accepts only a validated `ConversationContext`, ordered `Obligation[]`, matching terminal `ResolvedObligation[]`, required `SemanticGuidanceGate[]`, and the ordered authoritative `AuthorizedAction[]` projection from Ticket 62. It performs no reads and no interpretation.

The resulting `ResponsePlan` contains only the minimum composer contract: context ID and locale; obligation order; structured coverage; canonical facts; deterministic policy outcomes; cleared guidance; bounded conversational-generation semantics; bounded uncertainties; clarification and deferred requirements; actions; and explicit prohibited claims. It deliberately excludes raw context, resolved obligations, and the former `permitted_reasoning` placeholder, so blocked or indeterminate guidance cannot enter composer-readable expressive material.

Guidance is permitted only for an exact matching cleared Ticket 64B gate. The builder uses `gateMatchesTerminalResult()` against the supplied terminal guidance result; an unbound legacy gate, foreign obligation, or same-obligation substituted payload fails closed. Blocked guidance becomes `withhold_safety`; indeterminate guidance becomes `withhold_indeterminate` plus `guidance_gate_indeterminate`. Resolver failures and unresolved support are represented as bounded unavailable handling.

Ticket 65A.0 adds `practical_guidance_unknown` for a terminal Ticket 63 practical-guidance `bounded_unknown` with no source: no eligible reviewed practical guidance established an answer. It is not `canonical_fact_unknown` (canonical truth could not establish a fact), `resolver_failure` (resolution failed operationally), or `guidance_gate_indeterminate` (guidance exists but safety clearance is indeterminate). The builder, which still has validated obligation categories and terminal results, creates this reason only for practical guidance; the standalone ResponsePlan validator requires source absence and the closed reason vocabulary but intentionally cannot re-prove an omitted upstream category.

Ticket 65A.1 completes the practical-guidance lifecycle at this final boundary. Its one-result-per-obligation input accepts a practical obligation only with its Ticket 63 terminal `reviewed_knowledge`, `generated_guidance`, `bounded_unknown`, or `resolver_failure` result; the earlier Ticket 62 `deferred` / `reviewed_knowledge_or_reasoning` result is rejected as incomplete rather than silently overlaid or hidden. Final `required_coverage` therefore has no `deferred_practical_guidance`, and final `deferred_obligations` excludes `reviewed_knowledge_or_reasoning`. Other legitimate deferred stages—conversational generation, support resolution, and social response composition—remain unchanged. The finished-plan validator structurally forbids the removed practical-deferred vocabulary, while the builder remains responsible for category-aware terminal-state and Ticket 64B digest matching because upstream terminal inputs are intentionally absent from the finished plan.

Ticket 65B adds `conversational_generation`. It has exactly one entry, in obligation order, for every `conversational_handling` coverage item and no entry for any other handling. Each entry copies only the Ticket 61C operation and current-turn inputs/constraints, and dereferences only that obligation's explicitly selected Ticket 60A artifact IDs into `{ artifact_id, text }`. It never reads ordinary history, adds lineage ancestors, or exposes unrelated retained artifacts. This is non-authoritative customer-expressible material: it cannot populate facts, policy, safety, uncertainty, or actions. A future Ticket 66 Composer may consume this collection without reconstructing the task from raw context, evidence, reason codes, or actions.

Ticket 65C adds `commercial_semantics`. It has exactly one entry, in obligation order, for every `commercial_handling` item and no entry for any other handling. A closed, versioned deterministic mapping recognizes only the current standard checkout authorization and GLP-1 holding-page authorization, producing `semantics_version: ticket-65c-v1`, `checkout_offer` or `holding_page_offer`, and `destination.status: authorized_to_provide`. The explicit version crosses the Composer boundary with the closed vocabulary. Commercial semantics describe what the customer may be told about the commercial next step; `authorized_actions` describe what the system may do. Neither establishes action execution, destination availability, delivery, or any product/commercial fact. Concrete URLs remain unavailable until a later authorized execution/integration stage and are not fabricated here.

The deterministic builder operates on validated Ticket 61C obligations and the validated Ticket 60A `ConversationContext`. It enforces selected-artifact membership in that bounded context and projects exactly each selected artifact's canonical bounded text. The standalone finished-`ResponsePlan` validator enforces the closed structural contract, operation cardinalities, uniqueness, and one-to-one ordered alignment with `conversational_handling` coverage. Because a finished plan deliberately excludes raw `ConversationContext` and `Obligation[]`, that validator does not independently re-prove artifact membership, artifact-text equality, or operation equality against those upstream inputs. This is intentional: Ticket 66 consumes the bounded plan and must not regain unrestricted `ConversationContext` access.

For commercial semantics, the builder validates the upstream deterministic-policy/action combination against the Ticket 65C mapping before projection. The standalone validator enforces only the closed entry shape, intent vocabulary, destination authorization status, uniqueness, and commercial-coverage alignment; it cannot re-prove the excluded policy/action mapping after plan construction.

The central schema conditionally couples permitted-guidance authority to source type and requires non-empty reviewed references for reviewed guidance. The executable validator additionally verifies each reviewed guidance unit's reference IDs belong to that entry's reviewed-reference array; JSON Schema cannot safely express that sibling-array membership relationship without non-portable global logic.

The shared `schedule_reminder` vocabulary is retained for future compatibility, but it is not executable in the v2 launch contract: the builder rejects it as an obsolete authorized-action projection. Each final launch action must carry the Ticket 59B stable identity and executor idempotency key from Ticket 62; the builder validates and preserves that exact ordered projection, never synthesizing or rewriting either identity.
