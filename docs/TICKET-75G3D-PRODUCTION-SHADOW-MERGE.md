## Merge boundary

The tool takes a fresh export, the repository's closed Ticket75 topology
definition, an output candidate path, and a manifest path:

```bash
node scripts/merge-ticket-75g3d-production-workflow.js \
  /safe/operator/export.json \
  n8n/candidates/Ticket75G3D-Dietavity-Sales-Engine-shadow-candidate.json \
  n8n/candidates/Ticket75G3D-Dietavity-Sales-Engine-preservation-manifest.json
```

It fails closed unless the export has the expected workflow ID, active state,
Global Error Handler association, acquired and busy claim seams, protected
nodes, legacy transport/completion nodes, valid edges, and unique node names
and IDs.  It also rejects a merge that removes the error handler association,
changes a protected node, alters the busy loop, or leaves an unclassified
difference.

## Activation safety and privacy

The candidate has `active: false`, while its environment-driven route defaults
to `SALES_ENGINE_V2_CONTROL=disabled` and has no cohort values.  Importing it
therefore cannot route a claim to Node by itself.

Shadow keeps legacy authoritative: signing failures, bounded Node failures,
timeouts, non-2xx responses, malformed responses, and diagnostic failures
each rejoin the pre-existing `Get User from Supabase` entry exactly once.
Shadow never reserves a v2 reply, transports, completes, releases, or
reconciles a claim.  The future live branch intentionally remains fail-closed
and has no legacy fallback.

RS256 uses an encrypted n8n `jwtAuth` credential reference only.  There is no
PEM, static bearer token, assertion, secret, or cohort identifier in the
candidate.  Diagnostics receive only the G.3B/F.1 allow-listed structural
projection and Node-returned invocation identity; they never receive prose,
contact/profile data, prompts, raw model/provider material, destinations, or
assertions.

This is a draft for a separately authorized deployment ticket.  It performs no
actions by itself.

1. Obtain a new production export immediately before any change. Confirm its
   ID, active state, error-workflow association, claim seams, and source SHA.
2. Run the merge tool against that new export. Review the preservation manifest
   and stop on any unclassified delta or protected-node change.
3. Verify the Node deployment, durable replay migration, F.1 diagnostics
   migration, private network boundary, and n8n RS256 credential binding are
   separately ready. Do not create a cohort yet.
4. If staging/inactive import is supported, bind only the credential reference
   and verify the candidate remains inactive with `disabled` routing.
5. Under an explicit production change authorization, update only the intended
   workflow while preserving its ID, settings, credentials, and Global Error
   Handler association. Confirm the imported topology and disabled state.
6. Keep the immediate pre-change export as rollback input. On any mismatch,
   restore that export under controlled change authority; do not attempt a
   hand edit or activate a shadow cohort as remediation.
7. Only after the controlled import is verified should the later Ticket75H
   ticket authorize one approved internal shadow cohort and execute drills.

Remaining prerequisites before shadow are controlled production deployment of
the Node runtime, G.3A replay store and F.1 diagnostic migration, n8n RS256
credential/configuration, private endpoint reachability, timeout/lease-budget
verification, an approved retention/access policy, a fresh export-and-merge
review, and the Ticket75H drill authorization.  None are satisfied merely by
committing this candidate.
